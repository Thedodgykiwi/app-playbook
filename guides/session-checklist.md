# Session checklist (read first, every session)

Every Claude session on an app follows this list, **including "quick fixes"
and sessions started for one small thing**. It is short on purpose: the
details live in the linked guides, but everything needed to keep the common
standards is here, so nothing depends on remembering to open them.

Why it exists: a session started for a quick spacing fix wrote its issue in
its own format and went straight to building (Edit 1 Job Board #25). The rules
were in the playbook, just not read.

## 1. Start

- [ ] The app repo **and** this playbook are attached; read the app's
      `CLAUDE.md` in full (it has app-specific rules and notes).
- [ ] `git checkout dev && git pull`. All work happens on `dev`
      (never `alpha`, `staging` or `main` directly).
- [ ] Read the app's **brief** (`docs/brief.md`): the goal, who it's for,
      v1 must-haves, "not now" list and plan. No brief yet? New app → run
      the kickoff (`new-app-kickoff.md`) before feature work; existing app →
      offer to draft one.
- [ ] **Catch up on progress** (another session may have changed things since
      the app's notes were written):
      - what's new: `git log --oneline -10` on `dev`, and the open issues
        (newest and `priority: high` first);
      - **where the stages are:** `promote.sh status` (promote skill) shows
        what's waiting between Dev → Alpha → Staging → Production;
      - **last deploy:** the latest `deploy.yml` run (GitHub tools,
        `actions_list`) succeeded; if it failed, say so before anything else;
      - progress against the brief: which v1 must-haves are ticked / still open;
      - **unfinished work** left by an earlier session: `wip/*` branches
        (`git branch -r --list 'origin/wip/*'`) and "Where I got to" comments
        on open issues; pick up from there rather than starting again;
      - **app behind the starter?** if `docs/starter-version.md` is missing or
        old, mention it once and offer an upgrade (`upgrading-an-app.md`);
        don't do it uninvited.
- [ ] **Tell the user where things are** in 3–5 plain lines before starting:
      stages (e.g. "2 changes on Dev not yet in Alpha; Production up to
      date"), last deploy OK or not, open issues worth knowing, unfinished
      work, next must-have from the brief. Skip only for a pure question.

## 2. Every request (bug, change, idea), however small

- [ ] **Choice card first** (AskUserQuestion): "Log it, build later" /
      "Log it + mock-up first" / "Build it now", recommended option first.
      Skip only if the user already said which ("log it", "mock it up",
      "just do it") or it's a question that changes nothing.
- [ ] **Create the issue before any code**, label `bug`, `feature`, `tweak` or
      `performance`, in exactly this layout (`issues.md`):

      **What's happening / what's wanted**
      <one or two plain sentences>

      **Where**
      <stage and place, e.g. "All stages, Job Queue cards"; device if known>

      **Expected**
      <what it should do or look like>

      **Reported by**
      <role: "us", "tester", "client"; never a name or email>

      **Notes**
      <optional: screenshots, links, history>

      ---
      _Generated by [Claude Code](https://claude.ai/code)_

  Don't describe the code fix in the issue: it records the problem, not the plan.
- [ ] A screenshot the user sent → save it to `docs/issue-images/` on `dev`
      and show it in the issue (`issues.md`).
- [ ] A bug caused by another issue's change → make it a **sub-issue** of that
      issue (`issues.md`).
- [ ] Check it against the brief: if it changes the goal, a must-have or the
      "not now" list, or conflicts with it, say so; with the user's OK update
      the brief (and its change log) in the same commit (`new-app-kickoff.md` §5).
- [ ] Bigger or visible change with more than one sensible design → mock-up
      first, built from the real app (`working-with-the-user.md`).

## 3. Build

- [ ] Small, focused change on `dev`; one issue per commit, message ends with
      `Issue #<n>` (not "Fixes").
- [ ] Run the **automatic check** (`node /home/user/app-playbook/tools/check-app.js
      --pages "<the app's screens>"`) and the app's own checks (its `CLAUDE.md`
      "Checks" lists both; `testing-and-testers.md`), then look at the change: screenshot at phone
      (~375px) and desktop, light and dark; measure alignment rather than
      eyeballing it (`design.md`).
- [ ] No errors in the browser console; nothing scrolls sideways on a phone.
- [ ] No secrets, emails or personal data in the repo or issues (public).

## 4. Finish

- [ ] Push to `dev`; if rejected, someone else pushed: fetch, read their
      commits, combine, re-check (`stages-and-releases.md`). Never force-push.
- [ ] Confirm the deploy succeeded and the live Dev page passes the check
      (`check-app.js --url <Dev link>`).
- [ ] **Save as you go, every change.** Sessions can stop without warning
      (usage limit, closed, computer reclaimed while idle) and only pushed
      work survives. Push each working step: to `dev` if safe, otherwise to
      `wip/<issue-number>-<short-name>` (never deployed).
- [ ] **The user wants to set this work aside**, however they put it (or the
      session can't finish): push what's done (as above), add a comment on the issue
      starting **"Where I got to:"** (done, not done, next step, branch) and
      confirm in one line: "Parked #<n> on <branch>; next step: …".
- [ ] Tell the user what changed and what was / wasn't tested, in plain English,
      ending with: `You can see it in action here: <Dev link>`.
- [ ] A must-have released to Production → tick it in the brief.
- [ ] Learned something useful beyond this app? Apply the **"any app?"
      test** (playbook `CLAUDE.md`): general lesson → the right playbook
      guide, written generically, committed to the playbook's `main`, said in
      one line; fact about this app only → the app's own `CLAUDE.md`.
- [ ] Promote to Alpha / Staging / Production only when the user asks
      (`promote` skill), with a "what to try" list for testers; Production
      always needs their explicit "yes" (`testing-and-testers.md`).
