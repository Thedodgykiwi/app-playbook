# Session checklist (read first, every session)

Every Claude session on an app follows this list, **including "quick fixes"
and sessions started for one small thing**. It is short on purpose: the
details live in the linked guides, but everything needed to keep the common
standards is here, so nothing depends on remembering to open them.

Why it exists: a session started for a quick spacing fix wrote its issue in
its own format and went straight to building (Edit 1 Job Board #25). The rules
were in the playbook, just not read.

## 1. Start

- [ ] The app repo **and** this playbook are attached; read the app's
      `CLAUDE.md` in full (it has app-specific rules and notes).
- [ ] `git checkout dev && git pull`. All work happens on `dev`
      (never `alpha`, `staging` or `main` directly).
- [ ] Look at what's new: `git log --oneline -10` and the open issues. Another
      session may have changed things since the app's notes were written.

## 2. Every request (bug, change, idea), however small

- [ ] **Choice card first** (AskUserQuestion): "Log it, build later" /
      "Log it + mock-up first" / "Build it now", recommended option first.
      Skip only if the user already said which ("log it", "mock it up",
      "just do it") or it's a question that changes nothing.
- [ ] **Create the issue before any code**, label `bug`, `feature`, `tweak` or
      `performance`, in exactly this layout (`issues.md`):

      **What's happening / what's wanted**
      <one or two plain sentences>

      **Where**
      <stage and place, e.g. "All stages, Job Queue cards"; device if known>

      **Expected**
      <what it should do or look like>

      **Reported by**
      <role: "us", "tester", "client"; never a name or email>

      **Notes**
      <optional: screenshots, links, history>

      ---
      _Generated by [Claude Code](https://claude.ai/code)_

  Don't describe the code fix in the issue: it records the problem, not the plan.
- [ ] A screenshot the user sent → save it to `docs/issue-images/` on `dev`
      and show it in the issue (`issues.md`).
- [ ] A bug caused by another issue's change → make it a **sub-issue** of that
      issue (`issues.md`).
- [ ] Bigger or visible change with more than one sensible design → mock-up
      first, built from the real app (`working-with-the-user.md`).

## 3. Build

- [ ] Small, focused change on `dev`; one issue per commit, message ends with
      `Issue #<n>` (not "Fixes").
- [ ] Run the app's checks (its `CLAUDE.md` lists them, e.g. `npm run test:rules`,
      `npm run test:board`) and look at the change: screenshot at phone
      (~375px) and desktop, light and dark; measure alignment rather than
      eyeballing it (`design.md`).
- [ ] No errors in the browser console; nothing scrolls sideways on a phone.
- [ ] No secrets, emails or personal data in the repo or issues (public).

## 4. Finish

- [ ] Push to `dev`; if rejected, someone else pushed: fetch, read their
      commits, combine, re-check (`stages-and-releases.md`). Never force-push.
- [ ] Confirm the deploy succeeded and the live Dev page loads without errors.
- [ ] Tell the user what changed and what was / wasn't tested, in plain English,
      ending with: `You can see it in action here: <Dev link>`.
- [ ] Learned something useful beyond this app? Add it to the right playbook
      guide, commit to the playbook's `main`, and say so in one line.
- [ ] Promote to Alpha / Staging / Production only when the user asks
      (`promote` skill); Production always needs their explicit "yes".
